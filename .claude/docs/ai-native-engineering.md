# AI-Native 엔지니어링 시대의 프론트엔드 개발자로 일하기

이 문서는 petlog라는 코드베이스가 아니라, 이 코드베이스를 만들어가는 방식에 대한 기록이다. 기술 스택이나 기능이 바뀌어도 이 원칙은 유지한다.

## 핵심 전제

"무엇을 만들지, 왜 그렇게 만들지, 그게 맞는지 누가 검증할지"는 새로운 가치가 아니다. 좋은 엔지니어링은 항상 이걸 요구해왔다.

바뀐 것은 가치 자체가 아니라 **가격**이다. 예전엔 판단력이 타이핑 속도라는 자연스러운 마찰에 공짜로 얹혀 있었다. 코드를 손으로 짜는 데 시간이 걸렸기 때문에, 그 시간 동안 어쩔 수 없이 생각하게 됐다. 지금은 코드 생성이 거의 공짜가 되면서 그 마찰이 사라졌다. 판단력을 의도적으로 분리해서 연습하지 않으면, 그냥 사라진다.

## 핵심 원칙: 사라진 마찰을 스스로 다시 끼워 넣기

AI가 없애준 마찰(직접 코드를 읽는 시간, 검증하는 시간, 실패를 겪는 시간)을 어디에 의도적으로 되살릴지 스스로 설계하는 것이 지금 가장 훈련해야 할 스킬이다. 구체적인 실천 항목은 아래 "나의 판단 룰"에 정리했다.

## 사람이 책임지는 지점을 정하는 기준

AI가 설계·의도 단위의 검증까지 잘하게 되더라도, 그게 "그러니 사람이 필요 없다"로 이어지지는 않는다. 코드를 생성한 시스템과 검증하는 시스템이 같은 방식으로 학습됐다면 맹점도 같이 따라온다(correlated failure) — 사람의 가치는 AI보다 똑똑하다는 데 있는 게 아니라, **AI와 실패 모드가 다르다**는 데 있다. 그리고 무엇보다, "이 판단이 맞았는가"와 "틀렸을 때 누가 책임지는가"는 다른 질문이다. 후자는 지능이 아니라 역할·권한의 문제라서, 모델이 아무리 발전해도 사라지지 않는다.

그래서 실무에서는 "사람이 매번 판단할지 말지"를 그때그때 정하지 않고, 어떤 종류의 변경은 사람이 반드시 확인해야 하는지를 미리 룰로 박아둔다 — 되돌리기 어려운 정도, 텍스트 밖 맥락이 필요한 정도, 틀렸을 때의 대가, 누가 서명하는가라는 네 기준으로. 구체적인 항목은 아래 "나의 판단 룰"에 정리했다.

## 커리어 관점의 함의

- 구현 비용이 사라지면서, 판단 요구가 커리어 사다리의 훨씬 아래쪽(주니어)까지 내려온다. "시니어가 되면 그때 판단력을 기르면 된다"는 전략은 더 이상 유효하지 않다.
- 이력서·포트폴리오는 "AI를 잘 쓴다"가 아니라 **검증 가능한 판단의 흔적**(결정 문서, 트레이드오프 기록)으로 증명해야 한다.
- AI를 도구로 잘 쓰는 것을 넘어, AI 에이전트·워크플로우를 설계하고 조율하는 능력(`.claude/agents/`, `.claude/commands/`)이 시니어·리드 역량으로 이동한다.

## 나의 판단 룰

고정된 원칙이 아니라, 스스로 반복해서 검증하며 계속 다듬어가는 목록이다.

### 개발

1. **새 코드를 제안받으면 "이미 있는가"부터 확인한다.** 없다는 걸 직접 읽어서 확인한 다음에만 새로 짠다 (`decisions/026`이 이 룰의 실제 사례다).
2. **결론에는 항상 근거(파일:라인, 실행 결과)를 요구한다.** 근거 없는 결론은 "그럴듯함"이지 "맞음"이 아니다.
3. **커밋 전에는 diff 전체를 내 눈으로 훑는다.** 요청 범위 밖의 변경이 섞여 있으면 반드시 분리한다.
4. **되돌리기 어려운 액션(배포, 삭제, 외부 공개, 커밋/푸시)은 AI가 마지막 실행 버튼을 누르지 않는다.** 내가 확인하고 내가 실행한다.
5. **텍스트 밖 맥락이 얽힌 판단(비즈니스 우선순위, 법적 리스크, 조직 정치)은 스펙만 보고 끝내지 않는다.** AI에게 없는 맥락은 내가 직접 채운다.
6. **틀렸을 때 대가가 큰 지점(보안, 데이터 정합성, 사용자 신뢰)일수록 검증을 한 겹 더 둔다.** 대가가 작은 지점까지 똑같이 두텁게 검증하려 하지 않는다 — 마찰은 필요한 곳에만 되살린다.
7. **AI의 답이 내 직관과 다르면 먼저 반박해본다.** 반박이 무너지면 그때 받아들인다 — 반박 없이 받아들이는 게 가장 위험한 경로다.
8. **아키텍처·정책 판단에는 이유를 문서로 남긴다.** 나중의 나 또는 다른 사람이 "왜 이렇게 했는지"를 코드만 보고 복기할 수 없다면, 그건 아직 결정이 아니라 추측이다 (`decisions/`, `development-rules.md` 14번 규칙).
9. **범위를 스스로 좁힌다.** 요청받지 않은 범위(백엔드 스키마 확장 등)까지 손대고 싶은 유혹이 들 때, 그게 정말 필요한지 먼저 되묻는다.

### 제품/비즈니스

기술 판단 룰만으로는 "잘 만들었는가"는 검증되지만 "만들 가치가 있었는가"는 검증되지 않는다. `project-context.md`의 우선순위(사용자 가치 → 제품 완성도 → 유지보수성 → 확장 가능성 → 기술적 흥미)를 실제 판단 순간에 적용하기 위한 룰.

1. **기술적으로 흥미로운 선택과 제품 가치가 충돌하면 제품 가치가 이긴다.** "이 구조가 더 우아하다"는 이유만으로 범위를 넓히지 않는다 — 오늘 근거 추적(citation) 스키마 확장을 보류한 것처럼.
2. **제품 포지셔닝을 기술 결정보다 먼저 확인한다.** petlog는 "의료 진단이 아니다"가 포지셔닝이므로, AI 리포트의 문구·톤·실패 메시지는 이 제약 안에서만 결정한다 — 포지셔닝을 몰랐다면 나올 수 없는 판단이다.
3. **비용은 기능을 설계하는 단계에서부터 판단 기준에 넣는다.** AI 호출처럼 사용량에 비례해 비용이 늘어나는 기능은 "동작하는가"뿐 아니라 "무제한으로 허용해도 되는가"까지 같이 결정한다(`decisions/014`의 월 1회 제한이 그 예).
4. **실패·에러 상태도 제품 경험이다.** "정상 흐름이 되는가"만 확인하고 끝내지 않는다 — 실패했을 때 사용자가 다음에 뭘 해야 하는지도 설계 대상이다.
5. **새 기능을 만들기 전에 어떤 사용자 문제를 푸는지 한 문장으로 말할 수 있어야 한다.** 말할 수 없으면, 아직 만들 준비가 안 된 것이다.
6. **개인 프로젝트·포트폴리오라는 이유로 기준을 낮추지 않는다.** "포트폴리오에 보여주기 좋은가"가 아니라 "실제로 쓰는 사람에게 좋은가"를 기준으로 삼는다.
7. **신뢰를 깎는 방식으로 수익화하지 않는다.** 무료/유료 경계, 수익 구조를 정할 때 사용자 신뢰가 먼저 무너지면 수익화 자체가 불가능해진다는 것을 전제로 판단한다.

## 스스로 점검하는 신호

다음 신호가 보이면 마찰을 다시 끼워 넣어야 할 때다.

- 왜 이렇게 했는지 한 문장으로 설명 못 하는 코드가 쌓인다
- 커밋 직전 diff를 훑어보지 않고 올린다
- AI가 제안한 구조를 "그럴듯해서" 채택하고, 기존 코드를 확인하지 않는다
- 실패했을 때 사용자가 뭘 해야 하는지 스스로 답을 못 한다
