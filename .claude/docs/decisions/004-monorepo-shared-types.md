# Decision: 모노레포 + 공유 타입 레이어 (libs/)

## Status

`libs/types`, `libs/utils` 부분은 폐기됨 (2026-08-19). `011-graphql-code-first-migration.md`
이후 백엔드 스키마에서 SDL이, 프론트엔드에서 graphql-codegen 타입이 각각 생성되면서
"타입 단일 출처"를 GraphQL 스키마가 담당하게 됐고, 손으로 쓴 공유 타입은 어느 쪽에서도
import되지 않는 채로 남았다. 값이 어긋난 중복 정의(`AppetiteLevel`이 libs/types와
libs/ai에 서로 다른 값으로 존재)까지 생겨 오히려 혼란을 키웠다.

모노레포 구조 자체와 `libs/`(현재 `ai`, `mail`, `push`, `firebase`, `storage`, `seed`)는
유효하다 — 폐기된 것은 "도메인 타입을 손으로 정의해 공유한다"는 부분이다.
아래 원문은 당시 판단 기록으로 남긴다.

---

## Context

프론트엔드(Next.js)와 백엔드(NestJS)가 동일한 도메인 타입을 다룬다.

별도 레포로 분리하면 타입 동기화 문제가 발생한다.

---

## Problem

프론트엔드와 백엔드의 타입을 어떻게 공유할 것인가?

가능한 방향:

1. 각 프로젝트에서 타입을 독립적으로 정의
2. 별도 npm 패키지로 공유 타입 관리
3. 모노레포 내 libs/ 공유 레이어

---

## Decision

모노레포 구조로 프로젝트를 구성하고, `libs/types/`에 공유 도메인 타입을 정의한다.

구조:

```
petlog/
├── frontend/
├── backend/
└── libs/
    ├── types/   ← 공유 도메인 타입
    └── seed/    ← 개발용 시드 데이터
```

---

## Reason

### 타입 단일 출처

도메인 타입을 한 곳에서 관리하면 프론트엔드와 백엔드의 타입 불일치를 방지한다.

### 포트폴리오 관점

실제 서비스에서 모노레포는 일반적인 선택이다.

모노레포 구성 경험 자체가 포트폴리오 가치를 가진다.

### 배포 독립성 유지

libs/는 타입 정의만 포함한다.

런타임 의존성이 없으므로 프론트엔드와 백엔드의 배포는 독립적으로 유지된다.

---

## Trade-off

초기 설정이 단일 레포보다 복잡하다.

1인 개발에서는 과도한 구조일 수 있다.

하지만 타입 불일치로 인한 버그 비용이 더 크다고 판단했다.

---
