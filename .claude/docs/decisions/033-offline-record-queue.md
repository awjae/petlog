# Decision: 오프라인 기록 큐는 앱 셸 오프라인 지원 이후에 검토한다

## Status

결정됨 (2026-07-26). 도입 보류 — 선행 조건 아래 참고.

---

## Context

"모바일 우선 서비스이고 산책 중·병원에서 기록하는데 오프라인 대응이 없다"는 지적이
있었다. 네트워크가 끊긴 상태에서 기록을 저장하면 뮤테이션이 실패하고, 사용자는 다시
입력해야 한다.

---

## 확인한 사실

### 지금 오프라인이면 앱이 아예 뜨지 않는다

`mobile/capacitor.config.ts`는 **원격 URL 모드**다.

```ts
const config: CapacitorConfig = {
  appId: 'quest.petlog.app',
  server: {
    url: appUrl,           // 배포된 Next.js (ECS + CloudFront)
    cleartext: ...,
  },
};
```

로컬 웹 자산을 번들하지 않고, 웹뷰가 배포된 사이트를 그대로 로드한다. SSR과
`next.config.ts`의 rewrites를 유지하려고 선택한 구조다.

그 결과 **오프라인에서는 흰 화면이거나 웹뷰 로드 실패**다. 기록 화면에 도달할 수조차
없다. "저장한 기록을 큐에 넣었다가 나중에 보낸다"는 기능은 그 위에 얹을 수 있는 것이
아니다 — 얹을 앱 셸이 없다.

### 서비스워커도 없다

`app/manifest.ts`가 있어 웹 앱 매니페스트는 제공하지만(설치 가능), 서비스워커는 등록하지
않는다. `public/mockServiceWorker.js`는 MSW(개발용 API 모킹)이지 오프라인 캐싱과 무관하다.

---

## Decision

**오프라인 기록 큐를 지금 만들지 않는다.**

만들면 "네트워크가 없을 때 저장 버튼이 동작하는 것처럼 보이지만, 앱을 껐다 켜면 화면
자체가 안 뜨는" 상태가 된다. 사용자 입장에서 더 나쁜 경험이다.

이 기능은 단독 기능이 아니라 **선행 조건이 있는 기능**이다.

### 선행 조건

1. **앱 셸이 오프라인에서 떠야 한다.** 두 갈래가 있다.
   - (a) 서비스워커로 셸을 캐싱한다. 원격 URL 모드를 유지할 수 있지만, Next.js
     App Router 산출물(라우트별 청크, RSC 페이로드)의 캐싱 전략을 직접 설계해야 하고
     MSW 워커와 스코프가 겹치지 않게 관리해야 한다.
   - (b) 로컬 번들 모드로 전환한다. 오프라인이 확실해지는 대신 SSR과 rewrites를 포기해야
     한다. 공유 페이지의 서버 메타데이터(031, 링크 프리뷰)와 정면으로 충돌한다.
2. **큐의 정합성 규칙이 필요하다.** 기록은 `recordedAt`을 갖고 서버가 스트릭·캘린더를
   파생시킨다(030 참고). 오프라인에 쌓인 기록을 나중에 보내면 "어제 기록이 오늘 도착"하는
   상황이 생기고, 그 사이 다른 기기에서 같은 날 기록을 넣었을 수 있다. 중복 판정 기준
   (클라이언트 생성 ID + 서버 멱등 처리)을 먼저 정해야 한다.

---

## 도입 트리거

1. **Android 스토어 배포 이후 오프라인 이탈이 관측될 때.** 지금은 계측이 없어 "산책 중
   기록하려다 실패했다"가 실제로 얼마나 일어나는지 알 수 없다.
2. **앱 셸 오프라인 지원(선행 조건 1)이 다른 이유로 먼저 도입될 때.** 예를 들어 초기 로딩
   속도 개선을 위해 서비스워커를 넣게 되면, 그 위에 큐를 얹는 비용은 훨씬 작아진다.

---

## 지금 할 수 있는 값싼 대안

큐 없이도 "입력한 내용을 잃지 않는" 수준은 훨씬 싸게 만들 수 있다. 저장 실패 시 폼 값을
유지하고 재시도 버튼을 주는 것이다(현재 `useCreateHealthRecord`는 에러 문구만 보여준다).
네트워크가 잠깐 끊겼다 돌아오는 대부분의 경우를 이걸로 덮을 수 있고, 앱 셸 구조를 건드리지
않는다. 오프라인 큐보다 이쪽이 먼저다.
