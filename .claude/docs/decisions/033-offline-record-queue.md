# Decision: 오프라인 기록 큐는 앱 셸 오프라인 지원 이후에 검토한다

## Status

결정됨 (2026-07-26). 도입 보류 — 선행 조건 아래 참고.

---

## Context

"모바일 우선 서비스이고 산책 중·병원에서 기록하는데 오프라인 대응이 없다"는 지적이
있었다. 네트워크가 끊긴 상태에서 기록을 저장하면 뮤테이션이 실패하고, 사용자는 다시
입력해야 한다.

---

## 확인한 사실

### 지금 오프라인이면 앱이 아예 뜨지 않는다

`mobile/capacitor.config.ts`는 **원격 URL 모드**다.

```ts
const config: CapacitorConfig = {
  appId: 'quest.petlog.app',
  server: {
    url: appUrl,           // 배포된 Next.js (ECS + CloudFront)
    cleartext: ...,
  },
};
```

로컬 웹 자산을 번들하지 않고, 웹뷰가 배포된 사이트를 그대로 로드한다. SSR과
`next.config.ts`의 rewrites를 유지하려고 선택한 구조다.

그 결과 오프라인에서는 **웹뷰가 페이지를 새로 받지 못한다.** Android WebView의 HTTP
캐시가 남아 있으면 일부 자산이 캐시에서 뜰 수 있어 "무조건 흰 화면"이라고 단정할 수는
없지만, 서비스워커가 없으므로 오프라인 동작을 보장하는 장치는 어디에도 없다. 기록 화면에
안정적으로 도달할 방법이 없는 상태다.

`server.errorPath`도 설정하지 않아 로드 실패 시 WebView 기본 에러 화면이 그대로 노출된다.
이건 큐와 무관하게 지금 고칠 수 있는 항목이다.

"저장한 기록을 큐에 넣었다가 나중에 보낸다"는 기능은 이 위에 얹을 수 있는 것이 아니다 —
얹을 앱 셸이 보장되지 않는다.

### 서비스워커도 없다

`app/manifest.ts`가 있어 웹 앱 매니페스트는 제공하지만(설치 가능), 서비스워커는 등록하지
않는다. `public/mockServiceWorker.js`는 MSW(개발용 API 모킹)이지 오프라인 캐싱과 무관하다.

---

## Decision

**오프라인 기록 큐를 지금 만들지 않는다.**

만들면 "네트워크가 없을 때 저장 버튼이 동작하는 것처럼 보이지만, 앱을 껐다 켜면 화면
자체가 안 뜨는" 상태가 된다. 사용자 입장에서 더 나쁜 경험이다.

이 기능은 단독 기능이 아니라 **선행 조건이 있는 기능**이다.

### 선행 조건

1. **앱 셸이 오프라인에서 떠야 한다.** 두 갈래가 있다.
   - (a) 서비스워커로 셸을 캐싱한다. 원격 URL 모드를 유지할 수 있지만, Next.js
     App Router 산출물(라우트별 청크, RSC 페이로드)의 캐싱 전략을 직접 설계해야 하고
     MSW 워커와 스코프가 겹치지 않게 관리해야 한다.
   - (b) 로컬 번들 모드로 전환한다. 오프라인이 확실해지는 대신 SSR과 rewrites를 포기해야
     한다. 공유 페이지의 서버 메타데이터(031, 링크 프리뷰)와 정면으로 충돌한다.

     **대가가 그것만이 아니다.** 로컬 번들이 되면 웹뷰의 origin이 `capacitor://` 계열로
     바뀐다. 지금 API 호출은 상대 경로 `/api/graphql` + `credentials: 'include'`이고
     인증은 httpOnly 쿠키다. origin이 달라지면 rewrite도, 쿠키 전송도 성립하지 않아
     **인증 방식 전체를 다시 설계해야 한다**(토큰 저장 위치, CORS, 갱신 흐름). 앱 셸
     하나 때문에 인증을 갈아엎는 셈이라 이 갈래는 사실상 마지막 수단이다.
2. **큐의 정합성 규칙이 필요하다.** 오프라인에 쌓인 기록을 나중에 보내면 "어제 기록이
   오늘 도착"하는 상황이 생기고, 그 사이 다른 기기에서 같은 날 기록을 넣었을 수 있다.
   중복 판정 기준(클라이언트 생성 ID + 서버 멱등 처리)을 먼저 정해야 한다.

   여기서 흔들리는 값은 서버가 계산하는 집계(`Pet.todayRecordCount`, `recentWeight`,
   `CalendarEvent`)와 클라이언트가 `recordDates`로 세는 연속 기록일이다. 초안은 "서버가
   스트릭을 파생시킨다"고 적었는데 사실이 아니다 — 스트릭은 `homeDerive.ts`의
   `calcStreak`가 계산한다(030 참고). 어느 쪽이든 뒤늦게 도착한 기록이 과거 날짜를
   채우면 두 숫자가 함께 흔들린다.

---

## 도입 트리거

1. **Android 스토어 배포 이후 오프라인 이탈이 관측될 때.** 단, 지금은 계측이 없어 이
   조건 자체가 발동할 수 없다. 먼저 관측 수단을 만들어야 한다 —
   `useCreateHealthRecord`의 `onError`에서 `navigator.onLine`과 실패 종류를 구분해
   기록하면 된다(현재 `navigator.onLine` 사용처는 0곳이다). 한 줄짜리 작업이고,
   아래 "값싼 대안"의 (c)와 같은 지점이다.
2. **앱 셸 오프라인 지원(선행 조건 1)이 다른 이유로 먼저 도입될 때.** 예를 들어 초기 로딩
   속도 개선을 위해 서비스워커를 넣게 되면, 그 위에 큐를 얹는 비용은 훨씬 작아진다.

---

## 지금 할 수 있는 값싼 대안

초안은 "저장 실패 시 폼 값을 유지하고 재시도 버튼을 준다"고 적었는데, **그건 이미 되어
있다.** `records/new`와 `RecordForm` 모두 저장에 성공했을 때만 화면을 벗어나므로 실패
시 입력은 그대로 남고, 제출 버튼도 살아 있어 다시 누르면 재시도된다. 문구도 이미
"저장에 실패했어요. 다시 시도해주세요"다.

실제로 비어 있는 곳은 셋이다.

- **(a) 시트를 닫으면 입력이 사라진다.** `RecordBottomSheet`는 열릴 때마다 `sessionId`를
  올려 폼을 새로 마운트한다. 저장에 실패한 뒤 시트를 닫고 다시 열면 처음부터 다시 써야
  한다.
- **(b) 앱을 껐다 켜면 초안이 없다.** 실패한 입력을 로컬에 남기지 않는다. 큐 전체가
  아니라 "마지막 실패한 입력 하나"만 저장해도 체감 차이가 크다.
- **(c) 네트워크 실패와 서버 거절이 같은 문구다.** `navigator.onLine` 사용처가 0곳이라
  "지금 오프라인이에요"와 "값이 잘못됐어요"를 구분해 안내하지 못한다. 위 도입 트리거 1의
  관측 수단이기도 하다.

셋 다 앱 셸 구조를 건드리지 않는다. 오프라인 큐보다 이쪽이 먼저다.
