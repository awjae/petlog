# Decision: 서버 컴포넌트는 공개 화면에만 쓴다

## Status

결정됨 (2026-07-26).

---

## Context

"App Router를 쓰면서 RSC를 활용하지 않는다"는 지적이 있었다. `app/` 아래 tsx 33개 중
25개가 `'use client'`이고 `loading.tsx`는 0개다. 겉으로 보면 App Router의 껍데기만
쓰고 실제로는 SPA다.

이 문서는 "왜 그런가"를 답하고, 앞으로 어디까지 서버로 옮길지 경계를 정한다.

---

## 확인한 사실

### 정적 콘텐츠는 이미 서버 컴포넌트다

`'use client'`가 없는 파일은 다음과 같다.

```
app/layout.tsx
app/page.tsx            (랜딩)
app/terms/page.tsx      (이용약관)
app/privacy/page.tsx    (개인정보처리방침)
app/login/page.tsx      (메타데이터 + LoginPageClient 위임)
app/register/page.tsx   (동일)
app/not-found.tsx
app/opengraph-image.tsx
```

`features/legal/`의 `TermsContent`(158줄), `PrivacyPolicyContent`(195줄)도 클라이언트
지시자가 없다. "서버에서 할 수 있는 건 서버에서"라는 RSC의 실익 대부분은 이미 챙긴
상태였다.

**다만 약관 본문이 JS 번들에서 완전히 빠지는 건 아니다.** 같은 컴포넌트를
`LegalDocumentSheet`(`'use client'`)가 import하고, 그 시트를 회원가입 화면의
`AgreementSection`이 쓴다. 즉 `/terms`·`/privacy` 라우트에서는 HTML로만 나가지만,
`/register` 번들에는 약관 전문이 실린다. 이건 RSC 실익의 예시가 아니라 오히려 동적
import(029 패턴) 후보다.

### 클라이언트 렌더링으로는 원리적으로 못 하는 것이 하나 있다

**링크 프리뷰 봇은 JavaScript를 실행하지 않는다.** 카카오톡·슬랙·페이스북 봇이 페이지를
가져갈 때 HTML에 내용이 없으면 미리보기를 만들 수 없다. 공유 리포트 페이지가 전체
`'use client'`이기 때문에, 어떤 리포트를 공유해도 미리보기가 동일하다.

이건 성능 문제가 아니라 제품 문제다 — 공유가 이 서비스의 유일한 획득 경로다.

전환은 별도 PR로 진행 중이고, 이 문서가 머지되는 시점에 아직 반영되지 않았을 수 있다.
아래 결정 표의 "공유 리포트" 행은 그 PR을 전제로 한다.

### 인증 가드는 이미 엣지에 있다

`frontend/src/proxy.ts`(Next.js 16에서 `middleware.ts`를 대신하는 파일)가
`PROTECTED_PREFIXES`에 대해 `access_token` 쿠키 존재를 검사하고 리다이렉트한다.
클라이언트 JS 실행 전에 서버 엣지에서 처리되므로, **비로그인 방문자**에게는
"보호 화면이 CSR이라 잠깐 보인다"는 문제가 없다.

다만 이 가드는 쿠키의 존재만 보고 서명·만료는 검증하지 않는다(실제 검증은 이후 GraphQL
`GqlAuthGuard`). 그래서 **만료된 토큰**을 가진 재방문자는 엣지를 통과해 화면이 한 번
그려지고, 첫 쿼리가 401을 받은 뒤 `errorLink`가 `/login`으로 보낸다. 이 경로의 깜빡임은
남아 있고, 서버 렌더로 옮긴다고 해결되지도 않는다(서버가 토큰을 검증하려면 결국 API를
호출해야 한다).

---

## Decision

**서버 컴포넌트는 "비로그인 방문자·크롤러가 보는 화면"에만 쓴다.**

| 화면 | 렌더링 | 이유 |
| --- | --- | --- |
| 랜딩 / 약관 / 개인정보 | 서버 | 정적 콘텐츠. JS로 보낼 이유가 없다 |
| 로그인 / 회원가입 | 서버 껍데기 + 클라이언트 본문 | `metadata` export를 위해 |
| 공유 리포트 | 서버 껍데기 + 클라이언트 본문 (별도 PR에서 전환) | 링크 프리뷰 봇이 읽을 `<head>`가 필요 |
| 홈 / 기록 / 반려동물 / 리포트 / 설정 | 클라이언트 | 아래 참고 |

### 인증 화면을 클라이언트로 두는 이유

1. **SEO 가치가 0이다.** 로그인 뒤 화면이라 크롤러가 도달하지 않는다.
2. **상태 레이어와 충돌한다.** Apollo 정규화 캐시, `cache-and-network`, 리포트 폴링
   (`useReportPolling`), 뮤테이션 후 캐시 갱신이 데이터 흐름의 전부다. RSC로 옮기면
   서버 fetch와 Apollo 캐시가 이중 경로가 되고 "어느 쪽이 진실인지" 흐려진다.
3. **재방문 사용자에게 이득이 적다.** 주 사용 패턴이 Capacitor 웹뷰 재방문이라 셸이
   이미 캐시돼 있다.
4. **새 인프라 문제를 만든다.** 서버에서 API를 호출하려면 내부 엔드포인트와 쿠키 전달
   경로를 설계해야 한다. 지금 `NEXT_PUBLIC_API_URL`은 브라우저 기준 공개 도메인이다.

### `loading.tsx`를 쓰지 않는 이유

라우트 레벨 로딩 UI는 서버 컴포넌트가 데이터를 기다릴 때 의미가 있다. 데이터를 클라이언트
훅이 가져오는 구조에서는 라우트가 즉시 렌더되고 훅이 `loading`을 반환하므로, 화면별
스켈레톤(`ReportSkeleton`, `PetDetailSkeleton`)이 그 역할을 한다. 두 겹을 만들면 로딩
표시가 두 번 깜빡인다.

---

## 재검토 조건

- **공개 화면이 늘어날 때** — 예를 들어 반려동물 건강 정보 콘텐츠 페이지처럼 검색 유입을
  노리는 화면이 생기면, 그 화면은 처음부터 서버 렌더로 만든다.
- **비회원 방문자의 LCP가 문제가 될 때** — 공유 페이지는 지금 서버(메타데이터) +
  클라이언트(본문)로 두 번 조회한다. 서버에서 받은 데이터를 클라이언트 초기값으로 넘기면
  한 번으로 줄고 스켈레톤도 사라진다. 측정 후 판단한다.
- **Apollo가 RSC를 1급으로 지원할 때** — 현재는 별도 통합 패키지가 필요하고, 그 경계에서
  캐시 동작이 달라진다.
