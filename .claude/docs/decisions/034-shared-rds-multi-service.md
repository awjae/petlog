# Decision: RDS 인스턴스는 서비스 간 공유하고, 이름은 지금 바꾸지 않는다

## Status

**보류.** 두 번째 서비스를 실제로 만드는 시점에 이 문서를 다시 읽고 결정한다.
지금은 아무것도 바꾸지 않는다 — 코드 변경 없음.

이 문서는 "그때 무엇을 알고 있어야 하는가"를 기록해 둔 것이다. 2026-09-01에
비용 구조를 조사하다 나온 결론이며, 그 시점의 측정값을 함께 남긴다.

---

## Context

2026-09-01, AWS 크레딧이 소진되어 유료 전환되면서 비용 구조를 처음으로 들여다봤다.
7월 $63.50, 8월 $76.85가 크레딧으로 가려져 있었고, 실제로는 월 약 $69.47(약 10만원)이
청구되는 구조였다.

이때 "새 서비스를 하나 더 열면 또 10만원이 나가는가"라는 질문이 나왔고, 답은 아니었다.
$69.47의 대부분이 **한 번만 내면 되는 공용 인프라**이기 때문이다.

| 항목 | 월 비용 | 서비스 추가 시 |
| --- | ---: | --- |
| ALB (시간 $16.34 + 퍼블릭 IPv4 2개 $7.30) | $23.64 | 그대로 — 리스너 규칙으로 라우팅 |
| RDS (인스턴스 $18.18 + gp3 20GB $2.56) | $20.74 | 그대로 — `CREATE DATABASE` 하나 더 |
| Fargate 태스크 (컴퓨트 $8.26 + IP $3.65) | $11.91 × 2 | **여기만 증가** |
| Bastion EBS (인스턴스는 정지 상태) | $0.71 | 그대로 |
| CloudFront / S3 / ECR / Secrets Manager | $0.56 | 그대로 |

즉 **새 서비스의 한계비용은 $11.91(백엔드만) ~ $23.82(프론트 포함)** 이다.
서비스를 3개 돌려도 $93~117이며, 각각 독립 인프라로 만들었다면 $210이었을 것이다.

이것이 "단일 EC2로 바꾸면 월 $30 아낀다"는 안을 택하지 않는 실질적 이유이기도 하다 —
서비스가 늘수록 지금 구조의 한계비용이 훨씬 낮다.

---

## Problem

RDS 인스턴스를 서비스 간 공유하기로 하면, 이름 체계가 어긋난다는 지적이 나왔다.
"서비스별로 DB를 나눈다면 지금 DB 이름도 바꿔야 하지 않는가."

확인해보니 이름은 세 층으로 나뉘고, 층마다 답이 다르다.

| 층 | 현재 값 | 코드 위치 | 공유 시 |
| --- | --- | --- | --- |
| RDS 인스턴스 식별자 | `petlog-db-dev` | `infra/stacks/database-stack.ts:103` | 어긋남 (플랫폼인데 서비스 이름) |
| **데이터베이스 이름** | `petlog` | `infra/stacks/database-stack.ts:38,112` | **정확함** |
| 마스터 유저네임 | `petlog` | `infra/stacks/database-stack.ts:37` | 어긋남 + **변경 불가** |

---

## Decision

### 1. 데이터베이스 이름 `petlog`는 그대로 둔다

서비스별로 DB를 나눈다는 것은 인스턴스 안에 `petlog`, `<새서비스>` 식으로 여러
데이터베이스를 두는 구조다. 그 구조에서 petlog의 데이터베이스 이름이 `petlog`인 것은
정확하다. 새 서비스는 `CREATE DATABASE <새서비스>` 하나면 되고 충돌하지 않는다.

### 2. 인스턴스 식별자 `petlog-db-dev`는 그때 바꿔도 된다 — 지금 하지 않는다

`modify-db-instance --new-db-instance-identifier`는 recreate가 아니라 rename이라
데이터가 쌓인 뒤에도 동일하게 동작한다. 엔드포인트 DNS가 바뀌지만
`backend-stack`이 DATABASE_URL을 cross-stack reference로 조립하므로
`cdktf deploy` 한 번이면 자동 반영된다.

**지금 하나 2년 뒤에 하나 비용이 같다.** 그래서 지금 할 이유가 없다.

### 3. 마스터 유저네임 `petlog`는 영구히 두는 쪽으로 기운다

RDS는 생성 후 마스터 유저네임 변경을 지원하지 않는다. 바꾸려면 스냅샷 복원으로
인스턴스를 재생성해야 한다. 세 항목 중 유일하게 "지금이 가장 싼 시점"인 것은 맞다
(실데이터가 거의 없다).

그럼에도 바꾸지 않는다. **기능적으로 아무 문제가 없기 때문이다.** 이것은 인스턴스
관리자 계정 이름일 뿐이고, 실제 서비스 격리는 `petlog_app` / `petlog_migrator` 같은
서비스별 역할이 담당한다. 이름이 거슬린다는 이유만으로 DB를 재생성하는 것은
남는 장사가 아니다.

### 4. 두 번째 서비스를 붙이는 시점의 체크리스트

- [ ] `CREATE DATABASE <새서비스>`
- [ ] **`REVOKE CONNECT ON DATABASE <새서비스> FROM PUBLIC;`** ← 아래 "격리 구멍" 참고
- [ ] `<새서비스>_app` / `<새서비스>_migrator` 역할 생성 및 GRANT
- [ ] `infra/bootstrap/db-roles.sql`을 서비스명 파라미터로 일반화
      (현재 `petlog`에 하드코딩되어 있다 — `ALTER DATABASE petlog OWNER TO petlog` 등)
- [ ] 기존 `petlog` DB에도 `REVOKE CONNECT ... FROM PUBLIC` 소급 적용
- [ ] 인스턴스 식별자 rename 여부 판단 (선택)
- [ ] `FreeableMemory` 재측정 — 아래 "첫 병목" 참고

## 지금 확인된 사실 (2026-09-01 측정)

### RDS는 공유해도 될 만큼 비어 있다

```
커넥션        평균 4.6 / 최대 5.0     한도 약 112     →  4% 사용
CPU          평균 7.3% / 최대 39.1%                  →  여유 충분
여유 메모리    평균 198 MiB                            ←  가장 빡빡
스토리지       2.94 GiB / 20 GiB      30일간 증가 ~0
```

커넥션 한도는 `default.postgres16`의
`max_connections = LEAST({DBInstanceClassMemory/9531392}, 5000)`에서 계산한 값이다
(db.t4g.micro = 1 GiB 기준 약 112). 직접 관측한 값이 아니라 공식에서 유도한 값이다.

스토리지 2.94 GiB는 대부분 PostgreSQL 기본 설치와 WAL·로그 오버헤드이며, 실제 앱
데이터는 이 해상도에서 보이지 않는다. gp3 20 GiB는 RDS 최소 할당량이라 축소할 수 없다.

### 첫 병목은 CPU도 커넥션도 아닌 메모리다

여유 메모리가 198 MiB뿐이다. 서비스가 늘면 커넥션(5/112)이나 CPU(7%) 한계보다
**메모리가 먼저 걸린다.** 그 시점에 `db.t4g.small`(2 GiB, 약 $36/월)로 올려야 한다.

즉 "RDS 공유는 공짜"가 무한히 성립하지는 않는다. 대략 서비스 2~3개까지가 현재
인스턴스 크기의 범위로 보이며, 넘어가면 인스턴스 승급 비용($18 → $36)이 발생한다.

### 격리 구멍: `REVOKE CONNECT`가 없다

`infra/bootstrap/db-roles.sql`에 `REVOKE CONNECT ... FROM PUBLIC`이 없다.

PostgreSQL은 새 데이터베이스의 CONNECT 권한을 기본적으로 PUBLIC에 부여한다.
그리고 **역할은 데이터베이스별이 아니라 클러스터 전역**이다 — `petlog_app`은
인스턴스 레벨에 존재한다. 따라서 두 번째 서비스의 DB를 만드는 순간:

```
petlog_app       →  <새서비스> 데이터베이스에 접속 가능
<새서비스>_app    →  petlog 데이터베이스에 접속 가능
```

정확히 말하면 **접속과 카탈로그 조회(테이블 목록 등)까지만** 된다. 테이블 데이터는
별도 GRANT가 없으면 읽지 못한다 — 현재 스크립트의
`GRANT SELECT, INSERT, ... TO petlog_app`은 `petlog` DB 안에서만 유효하기 때문이다.
그래도 메타데이터가 새고, 커넥션 슬롯을 잡을 수 있다.

DB가 하나뿐인 지금은 드러나지 않는다. 서비스별 DB 분리를 실제로 하는 순간
실제 격리 구멍이 된다.

## Trade-off

### RDS를 공유하면 장애 반경도 공유한다

2026-08-31, RDS가 KMS 키 접근 실패로 스스로 정지해 약 24시간 로그인이 마비된 사고가
있었다(`Fixes PETLOG-API-2`, PR #61). 그때 서비스가 3개 얹혀 있었다면 3개가 동시에
죽었을 것이다.

백업·PITR도 한 덩어리다. 한 서비스 때문에 시점 복구를 하면 나머지 서비스의 데이터도
같이 되돌아간다. `backupRetentionPeriod`가 1일이라 복구 여지도 좁다.

**월 $20.74를 아끼는 대신 이 위험을 받는 것이다.** 개인 프로젝트 규모에서는 합리적인
거래로 판단하지만, 서비스 중 하나라도 실사용자가 붙어 매출이 생기면 이 계산은 다시
해야 한다.

### 인스턴스 이름을 안 바꾸면 코드가 오해를 부른다

`petlog-db-dev`라는 이름을 보고 "이건 petlog 전용 DB"라고 읽는 사람이 생긴다.
`database-stack.ts`의 주석으로 완화할 수는 있지만, 이름 자체가 주는 오해만큼
강하지는 않다. 두 번째 서비스를 붙일 때 rename을 진지하게 고려한다.
