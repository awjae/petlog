# Decision: 목록 페이지네이션은 임계치를 넘을 때 도입한다

## Status

결정됨 (2026-07-26). 도입 시점 미정 — 아래 트리거 참고.

---

## Context

"기록이 쌓이는 서비스인데 커서 페이지네이션도, 가상화도 없다"는 지적이 있었다.
프론트엔드에 `fetchMore` 사용은 0건이고, `client.ts`의 `typePolicies`에도 병합 정책
(`relayStylePagination` 등)이 없다.

도입 전에 "지금 실제로 무엇이 무제한인가"를 확인했다.

---

## 확인한 사실

### 대부분의 조회는 이미 경계가 있다

| 조회 | 경계 | 위치 |
| --- | --- | --- |
| 홈 스트릭(`recordDates`) | `limit` 인자, 기본 90 | `user.resolver.ts:47` |
| 캘린더(`calendarEvents`) | `startDate`~`endDate` 범위 | `user.resolver.ts:54` |
| 리포트 기간 조회 | 사용자가 고른 기간(최대 90일) | `reportPeriod.ts`의 `MAX_PERIOD_DAYS` |

### 경계가 없는 것은 하나다

`HealthRecordService.findAll()`은 `take` 없이 해당 반려동물의 전체 기록을 돌려준다.

```ts
const records = await this.prisma.healthRecord.findMany({
  where: { petId, deletedAt: null },
  orderBy: [{ recordedAt: 'desc' }, { createdAt: 'desc' }],
});
```

이 결과를 쓰는 화면은 반려동물 상세의 타임라인(`useHealthRecords`)이다.

### DB는 병목이 아니다

`schema.prisma`에 `@@index([petId, recordedAt(sort: Desc)])`가 있어 정렬 조회가
인덱스를 탄다. 문제가 생긴다면 쿼리 시간이 아니라 **응답 크기와 클라이언트 렌더링**
쪽이다.

### 지금 규모

출시 2~3일차(2026-07-23 AI 리포트 공개)라 사용자당 기록은 많아야 수십 건이다.
하루 3건씩 매일 기록해도 1년에 약 1,000건이고, 직렬화된 행이 200바이트 안팎이므로
그때의 응답이 약 200KB다.

---

## Decision

**지금은 도입하지 않는다.**

CLAUDE.md의 성능 원칙은 "최적화는 측정 기반으로 한다"이다. 수십 건짜리 목록에
Connection 타입과 커서 병합 정책을 넣는 것은 이 원칙을 정면으로 어긴다. 비용도 작지
않다 — GraphQL 스키마(`healthRecords`)를 Connection으로 바꾸면 프론트 쿼리, MSW 핸들러,
E2E가 전부 따라 움직여야 하고, 리포트 생성이 기간 내 **전체** 기록을 읽는 것과도
충돌한다(목록용 조회와 집계용 조회를 분리해야 한다).

---

## 도입 트리거

다음 중 하나가 관측되면 착수한다.

1. **한 반려동물의 기록이 500건을 넘는 사용자가 생긴다.** 응답 약 100KB 지점이고,
   모바일에서 목록 렌더링이 체감되기 시작하는 규모다.
2. **`healthRecords` 응답의 p95가 300ms를 넘는다.** Sentry 트레이스로 확인한다
   (샘플링을 1.0으로 올려둔 이유가 이 측정이다).
3. **타임라인 화면의 INP가 200ms를 넘는다.** 렌더링 쪽 병목이면 페이지네이션이 아니라
   가상화가 답일 수 있으므로, 어느 쪽인지 구분해서 본다.

### 착수 시 순서

1. **먼저 값싼 방법을 쓴다** — `findAll`에 기간/개수 상한 인자를 추가해 타임라인이 최근
   N일만 요청한다. 스키마 형태를 바꾸지 않으므로 MSW·E2E가 그대로 산다.
2. 1번으로 부족할 때만 커서 페이지네이션(Connection + `relayStylePagination`)으로 간다.
3. 목록용 조회와 리포트 집계용 조회를 그때 분리한다. 리포트는 기간 내 전체를 읽어야
   하므로 같은 리졸버를 공유하면 안 된다.

---

## 참고

이 결정은 "페이지네이션을 모른다"가 아니라 "지금 넣으면 측정 없는 최적화"라는 판단이다.
실제 데이터가 임계치에 닿는 순간 위 순서대로 착수한다.
