# Decision: next/dynamic 코드 스플리팅 — "마운트 게이트" 패턴

## Status

결정됨 (2026-07-26).

---

## Context

포트폴리오 코드 리뷰에서 프론트엔드 전체(`frontend/src`)에 `next/dynamic`이나
`React.lazy` 사용이 0건이라는 지적이 나왔다. 항상 필요한 게 아닌 컴포넌트
(공유 바텀시트, 온보딩 오버레이 같은 오버레이/시트류)도 전부 초기 번들에
포함되고 있었다. CLAUDE.md의 성능 원칙("최적화는 측정 기반으로 한다")에 따라
`ShareReportSheet`(`reports/[reportId]`)와 `OnboardingOverlay`(`home`)를
코드 스플리팅 대상으로 골라 실제로 번들을 측정하며 적용했다.

---

## Problem

1차 구현에서 두 컴포넌트를 `next/dynamic(() => import(...), { ssr: false,
loading: () => null })`로만 감쌌더니, 자동 코드 리뷰(Qodo)가 실제 결함을
지적했다.

- `ShareReportSheet`는 `isOpen=false`여도 JSX에 항상 존재하는 구조였다
  (내부적으로 `isOpen` prop을 보고 `null`을 반환하는 방식). `next/dynamic`의
  loader는 "이 컴포넌트가 렌더 트리에 등장하는 순간" 청크를 요청하지,
  컴포넌트 내부에서 `isOpen`을 어떻게 처리하는지는 전혀 모른다. 그 결과
  페이지 마운트 시점에 청크가 바로 요청되어, "공유 안 하면 청크를 안
  받는다"는 코드 스플리팅의 목적 자체가 무력화됐다.
- `loading: () => null`은 청크를 실제로 지연 로드하게 되는 순간(사용자
  액션 이후)에는 "클릭했는데 아무 반응이 없다"로 보일 수 있어, CLAUDE.md의
  "비동기 UI는 Loading/Success/Empty/Error 모든 상태를 고려한다" 원칙과
  어긋났다.

---

## Decision

사용자 액션 이후에만 의미가 있는 컴포넌트(바텀시트, 오버레이, 모달 등)를
`next/dynamic`으로 분리할 때는 두 가지를 함께 적용한다.

1. **분리 지점**: `next/dynamic(() => import(...).then(...), { ssr: false,
   loading: () => <Fallback /> })` — `loading`은 `null`이 아니라 배경 톤에
   맞춘 최소한의 로딩 인디케이터로 채운다.
2. **마운트 게이트**: 부모 컴포넌트에 "한 번이라도 트리거됐는가"를 나타내는
   불리언 상태(예: `shareSheetMounted`)를 따로 두고, 실제 트리거 액션(버튼
   클릭)에서만 `true`로 바꾼다. 컴포넌트 자체의 열림/닫힘은 기존처럼
   `isOpen` prop으로 하되, JSX에는 `{mounted && <LazyComponent ... />}`
   형태로 게이트를 건다. **한 번 `true`가 된 뒤로는 다시 `false`로
   되돌리지 않는다** — 닫을 때마다 언마운트했다가 다시 열 때 재마운트하면,
   컴포넌트 내부의 데이터 조회 훅(예: `useReportShare`)이 설정을 매번
   다시 조회해 불필요한 요청과 깜빡임이 생기기 때문이다.

`OnboardingOverlay`는 이미 `showOnboarding` 조건부로만 렌더링되는
구조라 마운트 게이트가 원래부터 걸려 있었고, `loading` fallback만 보강했다.

---

## Reason

### "항상 렌더링 + 내부에서 null 반환"과 "아예 렌더링 안 함"은 다른 문제다

컴포넌트 내부의 `isOpen ? ... : null` 같은 조건은 **렌더 출력**을
숨길 뿐, **모듈 자체가 필요한지**는 결정하지 못한다. `next/dynamic`의
로더는 부모가 그 컴포넌트를 렌더 트리에 올리는 순간 실행되므로, 코드
스플리팅의 이득을 실제로 보려면 "트리에 올릴지 말지"를 부모가 별도
상태로 결정해야 한다.

### 완전 언마운트 대신 "한 번 마운트되면 유지"

닫을 때마다 언마운트하는 방식도 고려했지만, 리뷰 과정에서 "매번 재요청이
생긴다"는 트레이드오프가 지적됐다. 첫 오픈 이후의 재요청 비용이 첫 로딩
지연을 피하는 이득보다 크다고 판단해, 최초 1회만 지연시키고 이후에는
계속 마운트 상태를 유지하는 절충을 택했다.

### 측정 결과

Turbopack `next build`는 webpack 시절의 "First Load JS" 표를 더 이상
출력하지 않아, `client-reference-manifest`에서 각 라우트가 동기적으로
필요로 하는 클라이언트 청크만 추려 직접 계산했다 (raw/gzip):

| 라우트 | Before | After |
|---|---|---|
| `/home` | 357.8KB / 108.4KB | 349.0KB / 104.8KB |
| `/reports/[reportId]` | 317.4KB / 96.0KB | 299.7KB / 90.8KB |

---

## Trade-off

- 새로 지연 로딩할 컴포넌트마다 "마운트 게이트 상태 + fallback UI"라는
  보일러플레이트를 반복해야 한다. 이 패턴을 적용하는 지점이 3곳 이상으로
  늘어나면 `useLazyMount` 같은 공용 훅으로 추상화하는 것을 검토한다.
- Turbopack 프로덕션 빌드가 표준 번들 리포트를 제공하지 않아 측정 스크립트를
  즉석에서 작성했다 — 앞으로 성능 회귀를 CI에서 자동 감지하려면 이
  측정 로직을 정식 스크립트로 남기거나 `--webpack` 빌드를 별도로 돌려
  표준 리포트를 받는 방식을 검토해야 한다.
- 마운트 게이트를 건 이후에도 청크 자체는 사용자가 클릭한 시점에야
  받기 시작하므로, 매우 느린 네트워크에서는 클릭 후 로딩 인디케이터가
  잠깐 보일 수 있다 — 의도된 트레이드오프이며, `loading` fallback으로
  "반응 없음"처럼 보이지 않게만 처리했다.
