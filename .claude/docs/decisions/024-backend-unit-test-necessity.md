# Decision: E2E가 있어도 backend 유닛테스트가 필요한 이유

## Status

결정됨 (2026-07-15)

---

## Context

`013-e2e-vs-frontend-integration-test.md`에 따라 인증 흐름 E2E(`auth.spec.ts`) 4개를
작성하고, 로컬 라이브 실행과 CI(`test-e2e` job, main push 시에만 실행) 연동까지 마쳤다.
이 과정에서 실제 앱 버그 2개(Playwright strict-mode locator, `OnboardingOverlay`가
클릭을 가로막던 문제)와 CI 인프라 버그 3개(libs 빌드 순서, bcrypt 네이티브 바인딩,
PORT 환경변수 상속으로 인한 포트 충돌)를 실제로 잡았다.

이 시점에 "E2E가 이미 실제로 버그를 잡아내는 걸 증명했는데, backend 유닛테스트가
따로 더 필요한가?"라는 질문이 나왔다.

---

## Problem

E2E(`auth.spec.ts`)는 로그인/회원가입/로그아웃/보호경로 리다이렉트 4개 시나리오뿐이다.
`report.service.ts`, `health-record.service.ts`의 내부 정책 로직 근처는 전혀 지나가지
않는다.

구체적으로, `report.service.ts`의 `assertValidPeriod`는 코드 주석에 "과거 실제로
버그가 났던 부분"이라고 명시돼 있는 로직이다(달력 날짜와 시각을 혼동해 정상적인
날짜 선택이 거부되던 버그). 그런데 이 로직에 대한 회귀 테스트는 유닛테스트로도
E2E로도 지금 이 순간까지 존재하지 않는다.

E2E로 이런 정책 로직(월 1회 생성 제한, 최소 기록 수/일수 게이팅, 기간 경계값,
7종 기록 타입별 필드 검증 등)의 모든 조합을 커버하려면:

- 매 케이스마다 브라우저를 띄우고 실제 DB에 그 조건에 맞는 데이터를 세팅해야 한다
- 경계값 테스트(9건 vs 10건, 6일 vs 7일 같은) 하나당 몇 초씩 걸려 케이스 수가
  늘어날수록 전체 실행 시간이 선형으로 증가한다
- 실패 시 "어느 계층에서 왜 깨졌는지"를 브라우저 스크린샷/네트워크 로그에서
  역추적해야 해서 디버깅 비용이 유닛테스트보다 훨씬 크다

---

## Decision

**E2E와 별개로 backend 유닛테스트를 추가한다.** 1순위로 `report.service.ts`,
`health-record.service.ts`부터 시작한다(`CLAUDE.md`의 테스트 우선순위: 1. 핵심
비즈니스 로직 2. 데이터 변환 로직 3. 사용자 핵심 흐름).

| | E2E | 유닛테스트 |
|---|---|---|
| 검증 대상 | 여러 계층이 실제로 연결되는지 (쿠키가 심기는지, 라우팅이 되는지) | 그 계층 안의 로직이 정책대로 맞는지 |
| 속도 | 브라우저+네트워크 왕복, 초 단위 | 밀리초 단위 |
| 실패 시 원인 추적 | 브라우저 상태 전체를 봐야 함 | 실패한 함수/분기가 바로 드러남 |
| 이번에 커버한 것 | 로그인/회원가입/로그아웃/보호경로 | (추가 예정) 기간 검증, 게이팅, 기록 타입별 필드 검증 |

---

## Reason

### 1. 이미 한 번 터졌던 버그의 회귀 테스트가 아직 없다

`assertValidPeriod`는 실제 버그 이력이 있는 코드다. E2E 4개 중 어느 것도 리포트
생성 화면 근처에 가지 않으므로, 이 버그가 재발해도 지금 상태로는 아무 테스트도
잡아내지 못한다.

### 2. E2E와 유닛테스트는 잡는 버그의 종류가 다르다

E2E가 실제로 버그 2개(strict-mode locator, OnboardingOverlay)를 잡은 것은 사실이지만,
둘 다 "UI 조작 흐름"의 문제였지 "정책 로직"의 문제가 아니었다. 반대로
`assertValidPeriod`류의 버그는 UI 흐름과 무관하게 특정 날짜/기록 조합에서만
드러나므로, E2E가 우연히 그 조합을 테스트하지 않는 한 영원히 안 잡힌다.

### 3. 테스트 피라미드가 지금 거꾸로 서 있다

지금 유일하게 존재하는 테스트가 E2E(피라미드에서 가장 비싸고 적어야 할 계층)뿐이고,
가장 저렴하고 많아야 할 유닛테스트가 0개다. `CLAUDE.md`가 "테스트 우선순위 1위는
핵심 비즈니스 로직"이라고 명시했는데 정작 1위가 비어있는 상태다.

### 4. `test-backend` job의 `--passWithNoTests`가 아직 안 지워졌다

`.github/workflows/ci.yml`의 `test-backend` job은 spec 파일이 0개라 항상
"통과는 하지만 아무것도 검증 안 하는" 상태다. 유닛테스트가 생기면 이 TODO 주석과
플래그도 정리한다.

---

## Trade-off

### 수용한 비용

- 두 계층(E2E + 유닛) 모두 유지보수 대상이 된다. 정책이 바뀌면 유닛테스트를,
  화면 흐름이 바뀌면 E2E를 각각 갱신해야 한다.

### 수용 이유

두 계층이 커버하는 버그의 종류가 겹치지 않으므로("E2E와 유닛테스트는 잡는 버그의
종류가 다르다" 참고), 하나로
합쳐서 비용을 줄일 수 있는 관계가 아니다. 유지보수 비용은 늘지만, 그만큼
더 넓은 범위의 회귀를 잡아낸다.

---

## 적용 범위

1순위: `backend/src/report/report.service.spec.ts`, `backend/src/health-record/health-record.service.spec.ts`
