# Decision: AI-native 전환 경계 — 실행은 기계에게, 판정은 사람에게

## Status

결정됨 (2026-07-25)

`.claude/docs/ai-native-engineering.md`가 "왜 사람의 판단이 필요한가"라는 원칙을 세웠다면,
이 문서는 **그 판단을 파이프라인의 어디에 배치할 것인가**를 정한다.

---

## Context

제품이 사용자에게 닿기까지는 **생성 → 검증 → 배포 → 관측 → 판단**의 루프를 돈다.

AI가 코드 생성 비용을 거의 0으로 만들면서 이 루프의 첫 단계만 빨라졌다. 나머지 네 단계가
사람의 손과 기억에 남아 있으면, **생성 속도가 올라간 만큼 뒷단이 병목이 되고 사고도 같이
늘어난다.** 실제로 검증이 푸시 뒤에 있던 시기에는 "푸시 → CI 깨짐 → 고쳐서 다시 푸시"가
연쇄로 반복됐다.

그래서 각 단계를 누가 맡을지 미리 정해둘 필요가 있다. 정해두지 않으면 그때그때의 판단에
맡기게 되고, 그때그때의 판단은 결국 "생략"으로 수렴한다.

---

## Problem

무엇을 기준으로 가르는가.

가장 자연스러운 발상은 **단계 단위로 배분**하는 것이다 — "생성·배포·관측은 AI, 검증·판단은
사람" 같은 형태. 직관적이지만 이 배분은 실무에서 무너진다.

- **"검증은 사람"** 으로 못 박으면 테스트·타입체크·린트 자동화를 부정하는 문장이 된다.
  검증의 대부분은 기계가 훨씬 잘한다.
- **"배포는 AI"** 로 못 박으면 되돌리기 어려운 액션의 방아쇠를 기계가 당기게 된다.
- **"관측은 AI"** 는 수집까지는 맞지만, 지표를 보고 무엇을 할지는 사람의 몫이다.

즉 **한 단계 안에도 기계가 할 일과 사람이 할 일이 섞여 있다.** 단계는 배분의 단위가 아니다.

---

## Decision

### 원칙: 단계가 아니라 성격으로 가른다

모든 단계는 **실행(execution)** 과 **판정(judgment)** 으로 쪼개진다.

> **실행은 전부 기계에게 넘긴다. 판정은 사람이 쥔다.**

| 단계 | 실행 — 기계 | 판정 — 사람 |
| --- | --- | --- |
| **생성** | 코드·테스트·설정·문서 작성 | 무엇을 만들 것인가, 요구사항이 맞는가 |
| **검증** | 타입·린트·테스트·빌드·보안 스캔·리뷰봇 실행 | 지적을 수용할 것인가, 머지할 것인가 |
| **배포** | 빌드·아티팩트 업로드·롤아웃·롤백 | 지금 내보낼 것인가 (승인) |
| **관측** | 수집·집계·이상 알림 | 이 숫자가 무엇을 뜻하는가 |
| **판단** | (자동화 대상 아님) | 다음에 무엇을 할 것인가 |

"판단"만 사람 몫인 게 아니라 **모든 단계에 사람의 판정 지점이 하나씩 있다.**
반대로 **모든 단계에 기계가 가져가야 할 실행이 있다.**

### 1차 판정: 산출물이 실행 가능한가

어떤 일을 기계에게 넘길 수 있는지 가르는 기계적 기준.

> **산출물을 실행 가능한 형태로 만들 수 있으면 넘긴다. 실행해서 틀렸음을 드러낼 수 없는
> 것은 사람이 쥔다.**

실행 가능한 산출물(테스트·스크립트·타입·플랜 출력)은 **틀렸을 때 스스로 그렇다고 말한다.**
반면 문서·주석·추정은 틀린 채로 통과한다. 검토자가 읽고 넘어가면 그걸로 끝이다.

따라서 자동화의 우선순위는 "얼마나 귀찮은가"가 아니라 **"틀렸을 때 누가 알아차리는가"** 로
정한다. 아무도 알아차리지 못하는 영역이 가장 먼저 실행 가능한 형태로 바뀌어야 한다.

이 기준의 실천적 따름정리:

- **두 번 이상 반복되는 절차는 문서가 아니라 스크립트로 만든다.** 문서는 실행되지 않으므로
  썩어도 아무도 모른다. 스크립트는 첫 실행에서 틀렸다고 말한다.
- **"이렇게 하세요"는 실행 가능한 형태로 바꿀 수 있는지 먼저 묻는다.**

### 2차 판정: 사람이 방아쇠를 당겨야 하는 네 가지

1차 판정을 통과했어도 아래에 해당하면 **실행은 자동화하되 방아쇠는 사람이 당긴다.**

1. **되돌리기 어렵다** — 배포, 삭제, 외부 공개, 머지
2. **텍스트 밖 맥락이 필요하다** — 비용, 계약, 법적 리스크, 제품 우선순위
3. **틀렸을 때 대가가 크다** — 보안, 데이터 정합성, 사용자 신뢰
4. **누군가 서명해야 한다** — 책임 주체가 필요한 결정

### 핵심 안티패턴: 승인과 실행을 함께 쥐는 것

**"사람이 쥔다"가 "사람이 전 과정을 손으로 한다"를 뜻하면 안 된다.**

되돌리기 어려운 액션이라는 이유로 절차 전체를 수동으로 남겨두면, 마찰이 필요한 곳(승인)이
아니라 필요 없는 곳(실행)에 붙는다. 그리고 그 마찰은 실행 빈도를 떨어뜨려 **피드백 루프
자체를 느리게 만든다.**

| 안티패턴 | 올바른 형태 |
| --- | --- |
| 사람이 배포 명령을 직접 친다 | 파이프라인이 실행, 사람은 승인 버튼만 |
| 사람이 기억해서 리뷰 도구를 호출한다 | 자동 실행, 사람은 결과를 판정 |
| 사람이 문서를 보고 절차를 따라 친다 | 스크립트가 실행, 사람은 실행 여부를 결정 |

### 게이트에 무엇을 쓸 것인가

머지·배포를 **막는** 게이트에는 **결정론적인 것만** 쓴다 — 타입, 테스트, 빌드.

리뷰봇·정적 분석처럼 **확률적인 결과는 게이트가 아니라 입력**이다. 사람이 판정할 대상을
좁혀주는 역할이지 판정 주체가 아니다. 확률적 도구를 게이트로 걸면 거짓 양성이 작업을 막고,
결국 게이트를 끄게 된다.

---

## Reason

**AI와 사람의 가치 차이는 지능의 높낮이가 아니라 실패 모드의 차이에 있다.**

코드를 생성한 시스템과 검증하는 시스템이 같은 방식으로 학습됐다면 맹점도 함께 따라온다
(correlated failure). 사람의 가치는 AI보다 똑똑하다는 데 있는 게 아니라 **AI와 다른 방식으로
틀린다**는 데 있다. 그래서 사람을 AI가 잘하는 일(실행·반복·형식 검사)에 배치하면 그 차이가
낭비되고, AI가 구조적으로 약한 일(맥락·책임·우선순위)에 배치해야 값이 나온다.

그리고 "이 판단이 맞았는가"와 "틀렸을 때 누가 책임지는가"는 다른 질문이다. 후자는 지능이
아니라 역할·권한의 문제라서 모델이 아무리 발전해도 사라지지 않는다.

배치의 목표는 결국 **AI의 출력을 사람이 검토하기 쉬운 형태로 만드는 것**이다. 실행 가능한
산출물은 스스로 틀렸다고 말하므로 검토 부담이 줄고, 사람은 남는 판단력을 실행으로 검증할 수
없는 곳에 쓴다.

---

## Trade-off

**얻는 것**

- 검증이 앞단으로 이동해, 사고를 친 뒤 고치는 연쇄가 구조적으로 차단된다
- "이건 자동화할까"를 매번 고민하지 않는다 — 1차 판정이 기계적이다
- 사람의 개입 지점이 명시적이라, 개입하지 않은 것이 **실수인지 판단인지 구분된다**

**잃는 것 / 감수하는 것**

- **자동화 자체가 새로운 실패 지점이 된다.** 자동화는 신뢰 대상이 아니라 **관측 대상**이다.
  조용히 잘못 동작하는 자동화는 없는 것보다 나쁠 수 있다.
- 게이트가 생기면 급한 수정이 느려진다. 탈출구를 **명령 한 줄 수준으로** 준비해두되,
  기본값은 게이트가 켜진 상태로 둔다.
- 배포 자동화는 CI에 배포 권한을 주는 것을 의미한다. 권한 위임 방식은 별도로 결정해야 한다.

이 원칙을 Petlog에 적용했을 때의 스냅샷 (2026-07-25).

| 단계 | 실행 자동화 | 사람 판정 지점 |
| --- | --- | --- |
| 생성 | ✅ 에이전트·커맨드 | 기능 우선순위 |
| 검증 | ✅ 타입·린트·테스트·빌드 (CI)<br>✅ PR 게이트 (브랜치 보호)<br>✅ 리뷰봇<br>❌ 인프라 코드 검증 | 리뷰 지적 수용 여부, 머지 |
| 배포 | ❌ **수동** | 배포 시점 |
| 관측 | ✅ 에러(Sentry)<br>❌ 제품 지표 | 지표 해석 |
| 판단 | — | 전부 |

**다음 순서** (의존 관계 순):

1. 인프라 코드 검증 — 유일하게 기계 검증이 아예 없는 영역
2. 배포 자동화 — 승인은 사람, 실행은 파이프라인
3. 제품 지표 계측 — 관측 없이는 판단이 감이다

## 재검토 트리거

- **자동화가 조용히 틀린 것을 통과시켰을 때** — 게이트를 늘리기 전에, 왜 실행 가능한 형태가
  아니었는지부터 본다
- **사람이 쥔 지점이 병목이 됐을 때** — 승인과 실행이 아직 분리되지 않은 곳을 찾는다
- **협업자가 생겼을 때** — "누가 서명하는가"의 답이 바뀌므로 2차 판정 전체가 달라진다
