# Decision: 디자인 토큰의 역할 분리와 명암 모드

## Status

결정됨 (2026-07-27). PR #13.

---

## Context

배포된 화면을 모바일 뷰포트로 직접 캡처해 훑어본 결과, 컨셉(크림 다이어리)과 빈 상태
설계는 쓸 만한데 **접근성(대비)** 과 **화면 간 일관성**에서 같은 종류의 문제가 반복됐다.
토큰 값으로 명암비를 계산해보니 주요 CTA와 링크가 WCAG AA(4.5:1)는 물론 큰 글씨
기준(3.0:1)에도 못 미쳤다.

| 조합 | 변경 전 |
|---|---|
| 흰 텍스트 on `--color-primary`(#6baed6) | 2.43:1 |
| primary 링크 텍스트 on 배경 | 2.13:1 |
| `--color-warning`(#e89a30) 텍스트 | 2.28:1 |
| `--color-success`(#34c759) 텍스트 | 2.03:1 |

`--color-primary` 하나가 배경으로 55곳, 텍스트 색으로 67곳에 쓰이고 있어 호출부를
개별 수정하는 방식은 불가능했다.

---

## Problem

근본 원인은 **하나의 토큰이 두 가지 역할을 겸하고 있었다는 것**이다.

`--color-primary`는 "버튼 배경"이면서 동시에 "링크 글씨 색"이었다. 파스텔 톤을 유지하려면
연해야 하는데, 글씨로 쓰려면 진해야 한다. 한 값으로 둘 다 만족시킬 수 없다.

같은 문제가 상태색에도 있었다. `--color-warning`을 글씨용으로 어둡게 바꾸자
`color-mix(warning 12%, transparent)`로 만들던 배지 **배경도 같이 어두워져** 대비가
3.86 → 3.95로 제자리였다. 값을 아무리 조정해도 개선되지 않는 구조였다.

---

## Decision

### 1. 색 토큰을 "역할"로 나눈다

- `--color-primary` : **기능색.** 버튼 배경 / 링크 / 아이콘처럼 글씨가 얹히거나 사용자가
  눌러야 하는 요소. 흰 텍스트와 4.5:1 이상을 보장한다.
- `--color-primary-light` : **틴트 배경.** 위에 `--color-primary` 텍스트가 올라온다.
- `--color-pet-*` : **장식용 파스텔.** 글씨가 얹히지 않는 면에만 쓴다. 그 위에 글씨를
  올려야 하면 `--color-on-pastel`(모드와 무관한 고정값)을 쓴다.
- `--color-control-on` : 스위치 ON 트랙처럼 **"켜짐"을 색 면으로 알리는 컨트롤.**
  손잡이가 항상 흰색이라 primary와 달리 다크에서도 진한 값을 유지한다.
- `--color-track` : 세그먼트 컨트롤처럼 **안으로 들어가 보여야 하는 트랙.** 선택된
  알약(`--color-surface`)이 항상 트랙보다 밝아야 눌린 상태가 읽힌다.

success / warning / danger도 같은 짝을 갖는다 — `--color-warning`(글씨) /
`--color-warning-light`(그 글씨가 얹히는 면). **글씨가 얹히는 면은 `color-mix`로 즉석에서
만들지 않는다.** 글씨색을 어둡게 바꾸면 `color-mix` 배경도 같이 어두워져 대비가 상쇄되기
때문이다. (`:active` 같은 순간 상태나 글씨가 없는 구분선은 `color-mix`를 그대로 쓴다.)

토큰 값 자체를 바꿨기 때문에 169곳의 호출부는 한 줄도 고치지 않았다.

### 2. 명암 모드는 `data-mode` 속성으로 결정한다 (미디어 쿼리 아님)

테마는 두 축이다.

- **팔레트**(`data-theme`): 파스텔 스카이 / 로즈 핑크
- **명암**(`data-mode`): 시스템 설정 따름 / 라이트 / 다크

`'system'`은 DOM에 그대로 심지 않는다. `matchMedia`로 해석해 `data-mode`에는 **항상
`light` 또는 `dark`만** 들어간다. CSS에는 `prefers-color-scheme` 분기를 두지 않는다.

첫 페인트 전 적용은 `app/layout.tsx`의 인라인 스크립트가 맡고(`<html suppressHydrationWarning>`),
그 뒤의 상태 관리와 시스템 설정 변경 구독은 `ThemeProvider`가 맡는다. 키와 기본값은
`shared/config/theme.ts`가 단일 출처다.

### 3. `[data-mode='light']` 하위 트리 오버라이드는 "앱 밖으로 나가는 산출물"에만 쓴다

`globals.css`의 라이트 블록은 `:root` 외에 `[data-mode='light']`도 받는다. 어떤 요소에
이 속성을 달면 문서가 다크여도 **그 하위 트리만 라이트 토큰**을 갖는다.

**이 속성은 앱 밖으로 나가는 산출물에만 쓴다.** 현재 사용처는 두 곳뿐이다.

- `features/report/utils/shareImage.ts` — 공유 이미지를 그릴 때 라이트 팔레트를 읽는 임시 요소
- `features/report/components/SharePreviewFrame.tsx` — 그 이미지의 미리보기

**화면 안에서 "여기만 밝게" 같은 용도로 쓰지 않는다.** 그렇게 쓰기 시작하면 다크 모드가
군데군데 뚫린 화면이 되고, 어떤 영역이 왜 밝은지 코드만 보고 알 수 없게 된다.
새로 쓰려면 "이 픽셀이 앱 밖으로 나가는가"를 먼저 답할 수 있어야 한다.

### 4. 대비 검증을 자동화한다

`frontend/scripts/check-contrast.mjs` (`npm run check:contrast`)가 `globals.css`의 토큰을
직접 읽어 **스카이/핑크 × 라이트/다크 4조합 × 24규칙**을 검사하고, 미달 시 exit 1 한다.
여기에 "다크 블록의 토큰은 모두 라이트 블록에도 있어야 한다"는 불변식 검사를 더한다
(3번의 하위 트리 오버라이드가 성립하기 위한 조건이다).

규칙에는 **화면에 실제로 존재하는 조합만** 넣는다. 그리고 **값을 읽지 못하면 실패로 센다** —
"검사할 수 없었다"가 "통과"로 처리되면 검사기가 없느니만 못하다.

---

## Reason

### 왜 미디어 쿼리를 안 쓰는가

사용자가 "라이트"를 골랐는데 OS가 다크면, `@media (prefers-color-scheme: dark)` 안의
선언과 `[data-mode='light']` 선언이 **캐스케이드에서 경쟁**한다. 이기게 하려면 특이도나
선언 순서에 의존해야 하고, 그 규칙은 파일이 길어질수록 지키기 어렵다.

`'system'`을 JS에서 미리 해석해 넣으면 CSS는 "지금 라이트인가 다크인가"만 알면 된다.
경쟁이 애초에 발생하지 않는다.

### 왜 검증 스크립트를 만들었는가 — 그리고 왜 규칙 선정이 핵심인가

테마가 2종 × 명암 2종으로 늘면서 "어느 조합에서 글씨가 안 보이는지"를 눈으로 확인하는
게 불가능해졌다.

1차 버전은 **4조합 전부 통과**했지만, 코드 리뷰에서 *"통과가 실제 접근성을 보증하지
못한다"* 는 지적을 받았다. 규칙 13개 중 다수가 **UI에 존재하지 않는 조합**(순수 surface
위 상태색)이었고, 정작 문제가 있던 조합(틴트 면 위 글씨, 트랙 위 라벨, 펫 컬러 위 글씨)은
규칙에 없었다. 지적된 Critical 4건은 전부 스크립트가 통과 처리한 지점이었다.

규칙을 실제 사용 조합으로 교체하자마자 **핑크 틴트(4.37:1)와 펫 컬러 위 글씨(4.24:1)가
새로 걸렸다.** 검증 도구의 가치는 "통과했다"가 아니라 "무엇을 보고 있는가"에 있다.

그 뒤 같은 실패가 **다른 경로로 한 번 더 재발했다.** 공유 이미지용으로 셀렉터를
`:root,\n[data-mode='light'] {` 처럼 두 줄로 쓰자, 마지막 줄만 읽던 파서가 `:root` 블록을
놓쳐 **92개 검사 중 56개를 건너뛰고도 "전부 통과"를 출력**했다. 값이 아니라 도구가 깨진
것이었고, 출력의 마지막 줄만 보고 통과로 판단한 탓에 커밋까지 됐다. 그래서 지금은
셀렉터를 콤마로 나눠 전부 등록하고, 값을 못 읽으면 실패로 센다.

### 왜 공유 이미지는 라이트 고정인가

공유 이미지는 앱 밖으로 나가는 산출물이다. 수의사에게 보내거나 갤러리에 저장되고,
**받는 사람의 화면 설정과 무관하게 남는다.** 보내는 사람이 다크 모드라는 이유로 검은
카드가 나가면 인쇄·전달 상황에서 읽기 어렵고 브랜드도 일관되지 않는다.

고정하는 건 **명암뿐**이다. 팔레트(스카이/핑크)는 사용자가 고른 것을 그대로 따른다.

미리보기도 함께 고정했다. 실제 결과물이 라이트인데 미리보기가 다크면 "보이는 것과
나가는 것"이 달라진다.

### 왜 라이트 값을 JS에 복사하지 않았는가

`shareImage.ts`가 색을 상수로 들고 있으면 토큰이 바뀔 때마다 두 곳을 고쳐야 하고,
한쪽만 고치면 조용히 어긋난다. 대신 `data-mode="light"`를 단 임시 요소를 body에 붙여
계산된 값을 읽는다. 루트의 `data-mode`를 잠깐 뒤집었다 되돌리는 방법도 있었지만,
그 사이에 다른 코드가 끼어들면 화면이 깜빡일 수 있어 피했다.

### 네이티브 상태 표시줄

`ThemeProvider`가 `resolvedMode`가 바뀔 때마다 `StatusBar.setStyle`을 호출한다.
**배경색(`setBackgroundColor`)은 건드리지 않는다** — targetSdk 35의 edge-to-edge에서
상태 표시줄이 웹뷰 위에 겹쳐지므로 배경은 이미 페이지가 그린 `--color-bg`이고,
실제로 문제가 되는 건 아이콘/시계 색이다.

---

## Trade-off

- **파스텔 컨셉의 일부를 버렸다.** primary가 `#6baed6` → `#2f7099`로 진해져 버튼과 링크의
  시각적 무게가 올라갔다. 배경·카드·펫 컬러의 파스텔은 유지했지만, 누르는 요소는
  더 이상 "연한 하늘색"이 아니다. 읽히지 않는 CTA보다 낫다고 판단했다.
- **검증 스크립트는 `globals.css`의 토큰만 읽는다.** TSX에 인라인으로 박힌 색은 구조적으로
  잡지 못한다(실제로 심각도 세그먼트의 iOS 기본색이 그렇게 살아남아 2.06:1이었다).
  그래서 **색은 반드시 토큰으로만 지정한다**는 규칙이 함께 필요하다. 이 한계는 스크립트
  주석에도 적어뒀다. 장기적으로는 `.tsx`의 hex 리터럴을 막는 lint 규칙을 검토한다.
- **인라인 테마 스크립트가 `shared/config/theme.ts`와 이중 관리다.** 번들 밖에서 실행돼야
  해서 import를 쓸 수 없다. localStorage 키가 갈리면 새로고침마다 테마가 튄다.
- **앱 시작 직후 짧은 불일치**: JS 실행 전까지는 Android 테마(`DayNight`)가 정한 상태
  표시줄 아이콘 색이 잠깐 보인다. 사용자가 OS와 다른 모드를 고른 경우에만 해당하고,
  스플래시 스크린이 대부분 가린다.
- **공용 UI 프리미티브(Button/Input/Card) 추출은 하지 않았다.** 94개 CSS 모듈을 건드리는
  별도 리팩터링이라 이번 변경(79파일)과 섞이면 리뷰가 불가능해진다. 화면마다 CTA 스타일이
  복붙되는 문제는 남아 있고, 독립 작업으로 다룬다.
