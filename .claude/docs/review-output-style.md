# 리뷰 결과 출력 규칙

`/review`, `/security-review`, `pr-reviewer` 에이전트가 공유하는 출력 형식이다.

리뷰 결과는 **GitHub PR 코멘트에 그대로 붙일 수 있는 형태**여야 한다.
읽는 사람은 바쁘다. 분석 과정이 아니라 결론만 필요하다.

## 분량

- **전체 20줄 이내.**
- **지적 하나당 1~2줄.** 문제와 수정 방향을 한 문장으로 붙여 쓴다.
- **본문에는 최대 5개.** 6개 이상 발견하면 심각한 것부터 5개만 쓰고,
  나머지는 마지막에 `그 외 N건` 한 줄로 남긴다 (아래 참고).
- 코드 블록은 수정 방향을 말로 설명하기 어려울 때만, 3줄 이내로.

## 쓰지 않는 것

- 검토 과정, 읽은 파일 목록, 체크리스트 항목 나열
- 문제없는 항목 언급 ("Pass", "이상 없음", "확인 완료" 섹션 금지)
- 비어 있는 섹션의 헤더

## 형식

```
### 리뷰: <대상 — PR 제목, 브랜치명, 또는 파일 범위>

<한 줄 총평 — 머지 가능 여부와 이유>

**🔴 머지 전 수정**
- `파일:라인` — 문제 → 수정 방향

**🟡 확인 필요**
- `파일:라인` — 이유

**💬 제안**
- `파일:라인` — 제안

**그 외 N건**
- `파일:라인` — 한 줄 요약
```

## 그 외 N건

5개 상한에 걸려 잘려나간 지적은 버리지 않는다.
`그 외 N건` 아래에 `파일:라인 — 한 줄 요약`으로 모아 남긴다.
잘라낸 게 없으면 이 섹션도 생략한다.

`<details>` 같은 HTML 태그는 쓰지 않는다. GitHub 코멘트에서는 접히지만
터미널에서 리뷰를 읽을 때는 태그가 그대로 보인다.

**단, 🔴(머지 전 수정)는 개수 제한을 받지 않는다.** Critical이 6개면 6개 다 본문에 쓴다.
상한에 걸려 `그 외`로 밀려나는 것은 🟡과 💬뿐이다.

## 확신도

확신이 서지 않는 지적은 🔴이 아니라 🟡에 넣고, 근거를 한 줄로 붙인다.
문제가 하나도 없으면 `### 리뷰` 헤더와 한 줄 총평만 출력한다.
