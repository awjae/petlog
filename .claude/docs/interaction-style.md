# Claude 상호작용 스타일 가이드

## 질문 해석

"머지해도 돼?", "서비스 운영 차원에서 문제 없어?"처럼 PR이나 변경의 안전성을 묻는 질문은
**제품 동작**, 즉 사용자가 실제로 겪는 결과를 기준으로 답한다. 배포 절차·인프라 순서 같은 다른
축은 따로 묻지 않았으면 본 답 뒤에 한 줄로만 붙인다.

직전에 조사하던 주제(예: 배포 스크립트)로 질문을 해석하지 않는다. "운영"을 배포 절차로 읽고
답했다가 "제품 서비스 차원에서 코드상 문제가 없냐"고 다시 질문받은 적이 있다.


## 꼬리질문 규칙

작업 완료 후 또는 계획 수립 후, 근거 있는 질문만 0~3개 제시한다. 근거 있는 게 없으면 생략한다.

---

## 언제 적용하는가

### 적용하는 상황 (큰 작업)

다음 중 하나 이상에 해당할 때 꼬리질문을 제시한다.

- 새로운 기능 또는 모듈을 구현했을 때
- 아키텍처 또는 설계 계획을 제안했을 때
- 여러 파일에 걸친 리팩토링을 마쳤을 때
- 데이터 모델 또는 API 구조를 변경했을 때

### 적용하지 않는 상황 (작은 작업)

형식적인 꼬리질문이 노이즈가 되는 상황은 생략한다.

- 오타 수정, 변수명 변경, 주석 수정 등 단순 수정
- 단일 파일의 사소한 스타일 변경
- 질문에 대한 설명 또는 코드 해석만 했을 때

판단 기준: 이 변경이 설계 결정을 포함하는가? 포함하면 적용, 아니면 생략.

---

## 질문 형식

작업 완료 후 마지막에 다음 형식으로 제시한다.

```
---

**추가로 고려할 점이 있습니다.**

1. [우려 또는 고려사항 질문 — 근거 포함]
2. ...
```

개수는 근거 있는 만큼만 쓴다. 1개여도 되고 0개면 섹션을 쓰지 않는다.

---

## 질문 기준

질문은 다음 관점에서 선택한다.

### 아키텍처 관점

- 이 변경이 기존 구조와 충돌하지 않는가?
- 도메인 경계를 지키고 있는가?

### 확장성 관점

- 향후 기능 추가 시 이 구조가 걸림돌이 되지 않는가?
- AI Provider 교체 또는 다른 확장 시나리오에서 유연한가?

### 제품 관점

- 사용자 경험에 부정적인 영향이 없는가?
- Edge Case나 에러 상황을 충분히 고려했는가?

### 운영 관점

- 배포 또는 마이그레이션 시 리스크가 있는가?
- 성능 또는 데이터 정합성 문제가 생길 수 있는가?

---

## 질문 품질 기준

질문 하나를 쓰기 전에 세 가지를 확인한다. 하나라도 아니면 버린다.

1. **근거** — 이번 세션에서 읽거나 실행해서 본 것(파일:라인, 로그, 수치)에서 나왔는가?
   "~할 수 있다"는 일반론은 근거가 아니다.
2. **결정** — 답에 따라 다음 행동이 달라지는가? 지금 안 정하면 비용이 생기는가?
3. **새로움** — 이미 처리했거나 앞서 말한 것, 이번 변경과 무관한 것이 아닌가?

머지·배포·PR 갱신 같은 단순 실행 뒤에는 실행 중 예상과 다른 것을 발견했을 때만 붙인다.

좋은 꼬리질문:

- 현재 작업에서 놓쳤을 수 있는 구체적인 문제를 지목한다
- "네 / 아니오"로 끝나지 않고 판단을 요구한다
- 이미 처리된 내용은 다시 묻지 않는다

나쁜 꼬리질문:

- "잘 동작하는지 확인하셨나요?" (막연함)
- "테스트는 필요하지 않으신가요?" (반복적)
- "추가 기능이 필요하신가요?" (범위 무관)
- "나중에 ~하면 걸림돌이 되지 않을까요?" (근거 없는 가정)
- "~규칙을 정해두는 게 좋지 않을까요?" (이번 작업에서 확인한 문제 없이 모범 사례만 나열)
