# 타임존 다루기

Petlog에서 날짜·시간을 다룰 때 읽는 문서다.

결정 자체(왜 Asia/Seoul 단일 타임존인가, 다국가 전환 시 무엇이 필요한가)는
[033-service-timezone.md](decisions/033-service-timezone.md)에 있다. 이 문서는 그 결정을
이해하고 따라 쓰기 위한 **개념과 지도**다.

---

## 1. 시간에는 두 종류가 있다

타임존 버그는 거의 전부 이 둘을 섞어서 생긴다.

### 순간 (instant)

전 세계가 동시에 겪는 한 점이다.

축구 결승 킥오프를 떠올리면 된다. 한국은 새벽 4시, 런던은 저녁 7시다.
**시계 숫자는 다른데 순간은 하나**다.

### 벽시계 숫자 (civil time)

장소가 있어야 뜻이 생기는 값이다.

아침 7시 알람은 다르다. 뉴욕에 가면 뉴욕 7시에 울려야 한다.
**숫자가 고정이고 순간이 움직인다.**

### 저장 방법이 다르다

| 종류 | 저장 | 표시 |
| --- | --- | --- |
| 순간 | UTC 하나 | 보는 사람 시계로 변환 |
| 벽시계 숫자 | 숫자 + **장소(IANA 문자열)** | 저장된 장소 기준으로 계산 |

벽시계 값을 "미리 순간으로 계산해서" 저장하면 안 된다. 나라가 서머타임 규칙을
바꾸는 순간 값이 저 혼자 움직인다.

> 내년 3월 "산티아고 아침 9시" 회의를 지금 순간으로 계산해 저장한다.
> 칠레가 서머타임 시작일을 한 주 옮긴다.
> 이제 그 순간을 산티아고 시계로 되돌리면 **아침 10시**다. 아무도 안 건드렸는데
> 약속이 움직였다.

## 2. Petlog에서 어느 쪽인가

| 값 | 종류 | 기준 시계 |
| --- | --- | --- |
| `Report.createdAt` | 순간 | — |
| `HealthRecord.recordedAt` | 순간 (사용자가 고른 날짜의 정오 앵커) | — |
| `Appointment.scheduledAt` | **벽시계** | **병원**의 시계 |
| `Vaccination.nextDueAt` | 벽시계 (날짜만 의미 있음) | 사용자 |

`Appointment`가 함정이다. "3시에 오세요"는 **병원 벽시계 3시**다. 사용자가 해외에
있다고 그 예약이 "새벽 1시"로 보이면 안 된다. 즉 여기 기준은 사용자가 아니라 병원이다.

지금은 사용자도 병원도 전부 한국에 있어 문제가 드러나지 않는다.

## 3. 서버는 왜 KST 계산이 필요한가

DB에는 **순간**만 들어 있다. 그런데 제품 규칙은 **달력 말**로 쓰여 있다.

- "**오늘** 기록 몇 개?" — 홈 화면
- "**이번 달**에 리포트 썼나?" — 월 1회 제한
- "접종 예정일이 **오늘**인가?" — 알림

그래서 어딘가에서 한 번 번역해야 한다.

```
달력 질문("오늘")  →  순간 구간("이 시각 이상 ~ 이 시각 미만")
```

**이 번역에만 장소가 필요하다.** KST가 등장하는 곳은 여기뿐이다.

### 안 고르면 UTC가 골라진다

"타임존을 안 쓰면 중립"이 아니다.

`new Date()` + `getMonth()`는 **프로세스 시계**를 읽고, ECS Fargate 기본값은 UTC다.
즉 아무것도 안 하면 **"UTC라는 나라의 달력"**을 쓰게 된다. 그리고 Petlog 사용자 중
UTC에 사는 사람은 0명이다.

## 4. 어떻게 계산하나

`backend/src/common/utils/date.ts`의 헬퍼를 쓴다. 직접 계산하지 않는다.

```ts
import { kstDayRange, kstMonthRange } from '../common/utils/date';

const { start, end } = kstDayRange();        // KST 달력 하루
const { start, nextStart } = kstMonthRange(); // KST 달력 한 달
```

둘 다 **입력도 출력도 UTC 순간**이다. KST는 함수 안에서만 잠깐 존재한다.

### 안에서 무슨 일이 일어나나

지금이 KST 9월 1일 새벽 2시(= `2026-08-31T17:00Z`)라고 하자.

```
① +9시간      2026-08-31T17:00Z → 2026-09-01T02:00Z
              (가짜 시각. 대신 UTC 자리에 '한국 벽시계 숫자'가 올라온다)

② 날짜만 읽기  getUTCFullYear/Month/Date → 2026년 9월 1일   ← 한국 날짜 확보

③ 자정 만들기  Date.UTC(2026, 9월, 1) → 2026-09-01T00:00Z

④ -9시간      2026-08-31T15:00Z   ← KST 9월 1일 00:00의 '진짜 순간'
```

JS `Date`는 달력을 **프로세스 시계 기준**(`getMonth()`)이나 **UTC 기준**
(`getUTCMonth()`)으로만 읽어준다. "서울 기준으로 읽어줘"가 없다. 그래서 순간을
9시간 밀어놓고 UTC로 읽는 것이다.

### 구간은 반열림으로 쓴다

```ts
where: { createdAt: { gte: start, lt: nextStart } }
```

`lte: end - 1ms` 같은 형태를 쓰지 않는다. 경계에서 조용히 틀린다.

## 5. 클라이언트는 KST를 박지 않는다

**서버만 제약을 진다. 클라이언트는 기기 시계를 그대로 쓴다.**

`frontend/src/shared/utils/date.ts`가 `Asia/Seoul`을 박지 않는 이유다. 사용자가
어디에 있든 그 사람이 기대하는 날짜가 나온다.

### 예외: 공유 리포트

`frontend/src/features/report/utils/reportFormat.ts`는 `Asia/Seoul`로 고정한다.
표시 대상이 **작성자가 고른 기간**이고, 서버(OG 이미지·메타데이터)와 브라우저
양쪽에서 렌더되기 때문이다. 보는 사람이 누구든 작성자가 고른 그 날짜여야 한다.

### 하지 말 것 (실제로 있었던 실수)

"다음 리포트는 N월 N일부터예요"의 날짜를 `Asia/Seoul`로 고정하려던 PR이 있었다
([#52](https://github.com/awjae/petlog/pull/52), 닫힘).

`nextAvailableAt`은 **버튼이 풀리는 순간**이다. 그렇다면 읽는 사람 시계로 보여주는
게 맞다.

| 보는 사람 | 실제 해제 시각 | 로컬 표기 | KST 고정 |
| --- | --- | --- | --- |
| KST | 9/1 09:00 | 9월 1일 | 9월 1일 |
| EDT | **8/31 20:00** | 8월 31일 | 9월 1일 ❌ |

한국 사용자에겐 아무 차이가 없고, 서쪽 지역에선 이미 풀린 걸 더 기다리라고 안내한다.

**판단 기준:** 그 값이 *작성자가 고른 것*이면 작성자 기준으로 고정하고,
*앞으로 일어날 일*이면 보는 사람 시계로 보여준다.

## 6. 테스트

`backend/jest.config.ts`가 `process.env.TZ = 'UTC'`로 배포 환경과 맞춘다.

**개발 머신(Asia/Seoul)에서는 일자 경계 버그가 안 잡힌다.** 프로세스 TZ를 따라가는
코드가 우연히 맞게 나오기 때문이다. 실제로 `countTodayRecords` 버그가 오래 살아남은
이유가 이것이다.

**타임존 경계를 검증하는 테스트**는 픽스처를 프론트가 실제로 보내는 형태로 만든다.

```ts
// 프론트가 보내는 값과 같다 (reportPeriod.ts는 Z 없이 파싱 → 브라우저 로컬)
function kst(wallClock: string): Date {
  return new Date(`${wallClock}+09:00`);
}
kst('2024-01-01T00:00:00'); // → 2023-12-31T15:00:00Z
```

`new Date(2024, 0, 1)`은 프로세스 TZ를 따라 테스트(UTC)에서 UTC 자정이 된다. 그 값은
**KST 경계를 넘지 않아** 경계 버그를 그냥 통과시킨다. "최근 90일" 프리셋이 거부되던
버그가 그렇게 숨어 있었다 (§7).

기간 길이 산술처럼 타임존과 무관한 검증은 `new Date(y, m, d)`를 그대로 써도 된다.

## 7. 지금까지 이 클래스에서 난 버그

| 증상 | 원인 | 고친 곳 |
| --- | --- | --- |
| KST 00~09시에 어제 기록이 "오늘"로 집계 | `setHours(0,0,0,0)`가 프로세스 TZ(UTC)를 따름 | `kstDayRange` 도입 |
| **"최근 90일" 프리셋이 거부됨** | 서버가 UTC 달력으로 시작일을 하루 앞으로 접어 **91일**로 계산 | `toCalendarDay` → KST |
| KST 9/1 00~09시에 월 1회 제한이 안 풀림 | 월 경계가 UTC 기준 | `currentMonthBounds` → `kstMonthRange` |
| 같은 날 리포트 2장 (KST 9/1 새벽 + 오전) | 위와 같음 — 조회 창이 밀리며 이미 쓴 리포트가 빠짐 | 〃 |

공통점: **개발 머신에서는 전부 정상이고 배포 환경에서만 틀렸다.**

## 8. 요약

1. 순간과 벽시계 숫자를 구분한다
2. 서버는 **달력 질문을 순간 구간으로 번역할 때만** KST를 쓴다 — `date.ts` 헬퍼로
3. 컨테이너 TZ는 UTC 그대로다. 서버 시계를 바꾸지 않는다
4. 저장·전송은 항상 UTC 순간
5. 클라이언트는 기기 시계. 단 *작성자가 고른 값*은 Asia/Seoul 고정
6. 타임존 경계를 보는 테스트는 픽스처를 프론트가 보내는 형태로
